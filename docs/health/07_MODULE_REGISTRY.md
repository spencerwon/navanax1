## How to read a recipe

- **Order.** Removal goes against the `depends on` edges: `cli` first; then `engine-v1`
  or `kb-v1`; `errors` once `engine-v1` is gone; `reference-v1` once `engine-v1` and
  `kb-v1` are gone; `process` last. The gate refuses a registry in which a module still
  depends on one that has been removed.
- **The ledger.** Every recipe runs `python3 tools/buglog.py --mark-removed <id>` while
  its entry is still registered. It adds `removed_with_module: <id>` to every entry of
  `docs/logs/bugs.yaml` that cites the module's paths or tests, and `buglog.py --check`
  then stops requiring those files to exist — for those entries only, and only once the
  module is no longer registered. Entries are never deleted (the ledger is append-only);
  the ids a recipe lists are a snapshot of the day it was written, and the command is
  what counts.
- **Live references.** `--check` scans the files that run or index the system (`src/`,
  `tests/`, `tools/`, `config/`, `.github/`, `pyproject.toml`, `README.md`,
  `docs/README.md`, `docs/health/README.md`, `04` and this page). Every one of them that
  names a module's paths, and is not itself removed first, must be named in that module's
  recipe — with the edit, or with the reason it stays. A recipe that forgets a file is
  red before anyone runs it.

## Accepted exceptions to HREQ-X-02

HREQ-X-02 says a module is removed by four steps — flag off, delete its paths, remove its
entry, gates green — and that a module needing more is not finished. Two recipes need
more, and are accepted as documented exceptions rather than hidden ones:

- **`engine-v1`.** Its recipe also edits the gate and CI steps that run its suite and its
  golden fixture, the `tests` of `reference-v1` (whose bytes the engine's tests verify),
  `config/health/base.yaml` (the fixture and generator keys and three comments),
  `pyproject.toml` (the package-data glob) and the README rows. The reason: the gate and
  CI steps *are* the module's own tests, wired into shared files, and HREQ-X-02 did not
  anticipate tests that live outside a module's paths; the configuration and packaging
  lines name its files because the repository's tooling has one file for each concern.
- **`cli`.** Its tests live in `kb-v1`'s self-test file, so its recipe edits a file it
  does not own. Moving them to a test file of its own would remove the exception
  (proposed for the next round).

Every other recipe's extra steps are the bookkeeping `04 §6.5` already counts — the gate
and CI steps, the ledger mark, regenerating this page.

## Adding a module

1. Branch `module/<id>`.
2. ADR under `docs/health/decisions/` (Status: Proposed).
3. Entry in `config/health/modules.yaml` with `enabled: false` and the removal recipe written **before** the code; `PYTHONPATH=src python3 -m health.registry --write-07`.
4. Expectations registered (WF-H-02) if the module changes what the model predicts.
5. Code, tests, docs; `MODEL_VERSION` bump and golden regeneration if the model changed.
6. `tools/gates.py` green (it runs `python -m health.registry --check`).
7. On a scratch copy, **run the removal recipe** and confirm gates stay green; note the result in the PR.
8. Pull request; Spencer approves; merge with the flag still off.
9. `enable/<id>` pull request flipping the flag; Spencer approves.

## Flags and what reads them

**The flag governs every surface** — `health.cli status` today, the app at M1. A surface
asks `health.registry.is_enabled(<id>)` before it shows a module's output and shows
"unavailable", with the reason, when the answer is no. With `engine-v1` off, `status`
prints `model unavailable (engine-v1 disabled in config/health/modules.yaml)` and
`expectations: skipped (engine-v1 disabled)` and does not import the engine; a registry
that cannot be read fails closed the same way. `kb-check` and `kb-summary` read no flag.

**The tests and the package still run.** A disabled module is imported by its own tests
and checked by every gate, so it stays verified while it is off; turning it back on is a
one-line change that cannot surface something broken.

**The merge is the code switch; the flag is the surface switch.** Merging a module
(flag off) puts its code under the gates; the `enable/<id>` pull request puts its output
on the surfaces. Reverting either undoes exactly that.

`status` also prints every module with its state, so a disabled module is visible rather
than merely absent. A flag that nothing reads is a `CFG` defect (`05 §3`), the same rule as
`docs/02 §3.6` item 4. `HEALTH_MODULES_PATH` replaces the registry path for tests only
(a test shows a surface with a module switched off without editing the real file);
nothing in the product sets it.
